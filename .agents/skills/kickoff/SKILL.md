# 初回指示（kickoff）

CEO からの最初の指示を受け、**社員を動かして成果物を出す**。

職種は3つ（リサーチ・ライター・レビュー）。**人数は職種ごとに変わる。**
このスキルでは **リサーチ3人 + ライター1人 + レビュー1人 = 5人**で動かす。

## 手順

### Step 0: 会社の前提を読む

`COMPANY.md` を読む。**社名が未記入（テンプレのまま）でも止まらない**。そのまま進めてよい。

読んだら CEO に1行で確認する:
> 「`<社名>`（`<何をする会社か>`）として5人を動かします（リサーチ3・ライター1・レビュー1）。」

### Step 1: リサーチ社員を**3人同時に**動かす（担当を分ける）

**`researcher` を3回呼ぶ。1回の応答でまとめて呼び、3人を同時に走らせる。**

分担の目的は**時短ではなく範囲**。3人にしても待ち時間は1人のときと同程度（実測 6〜9分）で、
**調査メモが1本から3本に増える**。全体の待ち時間は「3人の合計」ではなく
「**一番遅い1人**」で決まる（実測では③が最も遅く、8分26秒）。

**分担はどんな会社でも成立する軸で切ってある。** 会社の内容に合わせて言い換えないこと。

| 担当 | 調べること | 書き出し先 |
|---|---|---|
| **① 同じことをやっている会社** | この会社と**同じもの**を提供している先。名前・価格・提供内容・提供範囲を**一次情報（公式サイト）**で確認する | `output/research-1-competitors-<日付>.md` |
| **② 別の方法で解決している手段** | 同じ悩みを**違う手段**で解決しているもの。**お金をかけない方法**（自分でやる・家族に頼む・既にある無料の道具）も必ず含める | `output/research-2-alternatives-<日付>.md` |
| **③ 世の中の数字と、使う人の本音** | 公的統計・業界資料・制度・認証（**一次資料**）と、使っている人／やめた人の**不満・レビュー**。**この2つを突き合わせて考察する** | `output/research-3-market-<日付>.md` |

依頼文の型（`<担当>` と `<パス>` を差し替えて3通作る）:

> 「あなたの担当は **<担当>** です。`COMPANY.md` を読み、担当範囲だけを調べて **<パス>** に
> 書き出してください。担当外は他の人が同時に調べているので触らないでください。
>
> **調査の予算: Web 検索と Web 取得を合わせて10回まで。調べる対象は3〜4件まで。**
> 予算を使い切ったら、そこまでで成果物を書いてください。調べ足りなかったことは
> 『わからなかったこと』に『予算内で確認できなかった』と明記してください。
>
> 最後に『自分の担当から見えた、この会社が狙える隙間』を必ず書いてください。」

サブエージェントは**このチャットの会話を見られない**ので、依頼文には必ず
「`COMPANY.md` を読むこと」「担当範囲」「書き出し先パス」「**調査の予算**」の4つを含める。

> ⚠️ **予算を渡さないと3人とも際限なく掘る。** 実測（2026-07-26）では、予算なしで3人に
> 分担させたところ、各自が1人体制のとき以上に調べ（Web 26回 → **146回**）、
> 一番遅い人が **14分50秒** かかった。
> 担当を狭めると「範囲をやり尽くす」方向に動くため、**必ず上限を渡す。**
>
> 予算を渡した2回の実測では、3人とも **Web ちょうど10回**で止まり、
> 「予算内で確認できなかった」を自分から申告した。**狙える隙間の質は落ちなかった**
> （予算なし7点 → 予算あり5点で、中核の発見は両方が掴んだ）。
> 失うのは、大量に横断しないと出ない逆張りの発見1つ程度。

> **なぜ③だけ分けないか**: 統計と利用者の不満を**同じ人に持たせる**ため。
> 別々にすると「統計ではこう言われているのに、現場ではこう回避されている」という
> 横断的な発見が誰の頭にも生まれない。①②は列挙作業なので分けても質が落ちない。

### Step 2: 3人の完了を待って、ライター社員に書かせる

**必ず Step 1 の3ファイルが出そろってから呼ぶ。** ライターは調査結果を踏まえて書く。

- `writer` に依頼: 「`COMPANY.md` と **`output/research-1-competitors-<日付>.md`、`output/research-2-alternatives-<日付>.md`、`output/research-3-market-<日付>.md` の3つ**を読み、LP 文面を `output/lp-<今日の日付>.md` に書き出してください。**3人が挙げた『狙える隙間』を読み比べて、一番強いものを前に出してください。**」

**依頼文に3つのパスを必ず含める。** 渡さないとライターは `COMPANY.md` だけで書き、
調査で見つかった差別化点が LP に反映されない。

> **なぜライターは並列にしないか**: ライターは約1分で終わるので、リサーチを待たせても
> 全体はほとんど伸びない。それと引き換えに、調査に裏づけられた LP が手に入る。

### Step 3: レビュー社員に見せる

- `reviewer` に依頼: 「`COMPANY.md` と **リサーチ3ファイル**、`output/lp-<日付>.md` を読み、レビュー結果を返してください。**調査で見つかった差別化点が LP に反映されているか**を必ず見てください」

`reviewer` は**書き込みツールを持っていない**ので、返ってきた指摘を**あなた（秘書）が** `output/review-<今日の日付>.md` に保存する。

### Step 4: CEO に報告する

3〜5行で報告する。成果物の全文は貼らない。

```
5人が動きました（リサーチ3・ライター1・レビュー1）。
リサーチ3人が同時に調べ、その結果をライターとレビューが受け継ぎました。

1. リサーチ社員（3人同時）
   - 同じことをやっている会社 → output/research-1-competitors-YYYY-MM-DD.md（N件）
   - 別の方法で解決している手段 → output/research-2-alternatives-YYYY-MM-DD.md（N件）
   - 数字と使う人の本音     → output/research-3-market-YYYY-MM-DD.md（統計N件）
2. ライター社員 → output/lp-YYYY-MM-DD.md（3人の調査を踏まえてキャッチコピー3案）
3. レビュー社員 → output/review-YYYY-MM-DD.md（指摘N件・最重要は「…」）

次の一手: ①指摘を直す ②COMPANY.md を書き換えて作り直す ③社員を増やす
```

### Step 5: 次の一手を案内する

CEO が「指摘を直して」と言ったら、`writer` に**レビュー結果のパスを渡して**書き直させる。
これが「人間がルーターとして社員をつなぐ」ということの実演になる。

## 注意

- 途中でエラーが出ても止まらない。動いた社員の成果だけで報告し、失敗した社員は正直に伝える
- ネットワーク環境で Web 検索が使えない場合、`researcher` は「未検証」と明記して自分の知識で書く。それで正常
